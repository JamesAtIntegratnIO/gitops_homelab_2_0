* **Update**: **The CoreDNS `rewrite` that keeps the Kargo UI's login working is in git now, as the `coredns-host-config` addon.** It had been applied to the cluster by hand and existed nowhere else. Talos owns `kube-system/coredns` as bootstrap manifest `11-core-dns` and re-applies it on every boot and machine config change, so the line was one reboot from vanishing — and **`cluster.coreDNS` in the machine config carries only `disabled` and `image`, no Corefile field**, so the obvious "put it in the Talos config instead" does not exist. The addon owns the ConfigMap with `selfHeal: true`, which is what makes this durable rather than decorative: Talos still wins the instant after a reboot, ArgoCD reverts it within the sync interval, and CoreDNS's `reload` picks it up ~30s later, so a reboot costs minutes without the rewrite instead of losing it silently. `prune: false` on purpose — pruning that ConfigMap is a cluster-wide DNS outage. The body is Talos's own Corefile verbatim plus the one line, with the regeneration command in the file header so a Talos upgrade's Corefile changes do not get silently pinned to the old text. The clean version — `cluster.coreDNS.disabled: true` and own the whole Deployment — is now **staged rather than merely named**: the Talos patch is [live-coredns-disabled.yaml](../../matchbox/talos-machineconfigs/live-coredns-disabled.yaml) and the ServiceAccount/RBAC/Deployment/Service are a `coredns-workload` addon left `enabled: false`, both captured verbatim from Talos's own render so `kubectl diff` is empty and enabling it is an adoption rather than a restart of the cluster's resolver. **The order is the whole risk — ArgoCD takes ownership first, Talos is switched off second**, because the reverse leaves a window where Talos has stopped recreating CoreDNS and nothing else has started. It still needs a machine config change on all three nodes, so it waits for James. Two things the patch turned up: `cluster.coreDNS` really does accept only `disabled` and `image` — `talosctl validate` rejects `corefile`, `Corefile` and `extraConfig` as unknown keys, so "put it in the Talos config" was never an option — and **`talosctl patch mc --dry-run` prints the entire machine config as a diff, embedded PEM private keys included.**

* **Update**: **Split into a 1080p default and an opt-in 4K profile, and tuned `until_score` so a library-wide purge is possible without re-grabbing everything.** Targeting 2160p across the whole library was measured before it was applied, and the measurement stopped it: **68.5 TB on disk against 17.08 TB free**, with **91.4% of episodes and 76.8% of movies below the 2160p cutoff** — roughly 18,600 items and 200–320 TB of downloads. Worse than merely running out of space: an upgrade *deletes* the existing file on import, so it would have traded a complete 1080p library for a partial 4K one and stranded the rest, plus ~18,600 indexer hits in one burst. Now there are **two profiles per app** — `WEB-1080p`/`HD Bluray + WEB` as the library default with **no 2160p tier at all**, and `WEB-2160p`/`UHD Bluray + WEB` opt-in. Excluding 2160p from the default is deliberate: ranking it *below* 1080p makes Sonarr replace existing 4K files with 1080p (the bug from the previous revision), ranking it *above* makes every new grab chase 4K, and there is no third ordering — so the titles that should be 4K, including everything already at 2160p, move to the opt-in profile instead. **`until_score` is −1000, not the template's 10000**, and this is the load-bearing number: at 10000 essentially every file is cutoff-unmet and the first search re-grabs the library; at −1000 a clean release (score ≥ 0) is left alone and only the −10000 offenders — DV and DTS — fall below and become replaceable. **DV went back to a blanket block** after being briefly set to TRaSH's defaults; `DV Boost` matches any DV release by title, which is what makes the blanket form work. Measured blast radius for the purge itself: **1,052 movies (38.3%) and ~5,055 episodes (27.9%)** carry DV or DTS — and because upgrades replace in place, net disk stays roughly flat, which is why this purge is safe where the 4K one was not. The anime profile is left untouched: `min_format_score: 100` with `score_set: anime-sonarr` means a −10000 there risks starving grabs where dual-audio DTS is common.
