## Start here: one command needs running

The single largest remaining source of etcd load is **not fixable from git**:

```bash
kubectl annotate vclusterorchestratorv2s.platform.integratn.tech \
  -n platform-requests vcluster-media kratix.io/manual-reconciliation-
```

`kratix.io/manual-reconciliation: "true"` is a one-shot trigger Kratix is supposed
to clear after acting on it. It was set by `kubectl annotate` at
**2026-08-21T02:19:09Z** during the previous session's quick-wins work, and never
cleared — so Kratix has been re-triggering itself ever since.

The evidence is unambiguous:

| | before 02:19Z | after |
|---|---|---|
| `vclusterorchestratorv2s` PUT/s | **0.03** (flat for 7 days) | **12.7**, now ~8 |
| events POST/s | **0.21** | **13**, now ~8 |

It produced **202,435 `ReconcileStarted` events — 97% of every event in the
cluster.** Kratix logs show `reconciliation started → reconciling workflows →
reconciliation finished` several times a second, with `status.workflowsSucceeded`
flapping 0↔1.

The annotation is **not in git** (only `argocd.argoproj.io/tracking-id` is), so
removing it is clearing unmanaged manual state, not causing drift. An agent
session will likely have this blocked by the permission classifier — that is
correct, it is a live cluster write. Ask James to run it.

| patch | what it buys |

| `all.yaml` → `kubernetesTalosAPIAccess` | Prerequisite for etcd snapshots. Today the only recovery from etcd loss is the 2–3h rebuild. |

### 2. etcd is I/O-starved — the deepest problem here

Measured 2026-08-21. Still true after the write-loop fixes, because the cause is
disk, not volume:

| | 10.0.4.101 | .102 | .103 | target |
|---|---|---|---|---|
| p99 WAL fsync | **178 ms** → 128 ms | 62 ms | 15 ms | **< 10 ms** |
| p99 backend commit | **1.48 s** | 64 ms | 27 ms | < 25 ms |
| leader changes / 24h | 44 | 37 | 43 | ~0 |

All three nodes put `/var` — and so `/var/lib/etcd` — on the single `sda`,
sharing it with the OS, containerd images and logs. `talos-xez-xys` is **72%
busy at 85 ms average write latency**.

This is not cosmetic. It is what knocked `data-nfs-client-provisioner` over 35
times:

```
E0821 12:54:44 Failed to update lock: etcdserver: request timed out,
                possibly due to previous leader failure
F0821 16:15:57 leaderelection lost
```

Any leader-elected controller is exposed to the same thing. **Suspect this first
when a controller restarts for no local reason.**

Reducing write volume helps at the margin. The real fix is a dedicated fast
device for etcd — a hardware/Talos change, not a code one.

### 3. DNS — the cause of the vcluster restart storms

CoreDNS forwards everything it cannot answer to the Talos host resolver at
`169.254.116.108`. When that stalls, CoreDNS saturates and *cluster-internal*
resolution fails with it — the vcluster syncer then cannot resolve its own etcd,
the vcluster apiserver loses etcd, and every controller inside the vcluster
shuts down together.

Correlation, from Loki (count of the CoreDNS upstream-timeout line):

| window | crash burst? | timeouts |
|---|---|---|
| 08-05 09:00–09:20 | yes | 52 |
| 08-09 06:50–07:10 | yes | 299 |
| 08-16 06:35–06:55 | yes | 407 |
| three quiet windows | no | **0** |

**Talos owns the CoreDNS Deployment and Corefile as bootstrap manifests and
re-applies them**, so almost nothing here is fixable from git — a
PodDisruptionBudget was the one piece, and it is already in.

**Update 2026-08-21: the single-upstream part is now measured, and the patch is
written.** Scraping both CoreDNS replicas on `:9153` shows one and only one
`to=` target, with nothing behind it:

| counter | `…-f2tlz` | `…-gsh7d` |
|---|---|---|
| `coredns_proxy_healthcheck_failures_total{to="169.254.116.108:53"}` | 2,036 | 2,169 |
| `coredns_forward_healthcheck_broken_total` | 4,192 | 4,673 |

With a single upstream those are the same event — *the* upstream being unhealthy
**is** having no healthy upstream — and CoreDNS then forwards blind. Both
replicas agree within ~10% over ~5 months, so the fault is upstream, not in a
pod. Nothing in `matchbox/talos-machineconfigs/` sets
`machine.network.nameservers`, so the nodes take whatever DHCP hands out; the
default gateway on `eno1` is `10.0.0.1`.

[`matchbox/talos-machineconfigs/dns.yaml`](../matchbox/talos-machineconfigs/dns.yaml)
adds a second independent resolver. It is **queued, not applied** — it needs
`talosctl` like the other three, and it carries two pre-checks written into the
file, because the field *replaces* the DHCP list and Talos distributes queries
across upstreams rather than treating later ones as failover-only:

```bash
talosctl -n 10.0.4.101 get resolvers   # confirm the real primary before applying
```

Owning CoreDNS outright (`cluster.coreDNS.disabled: true` + a CoreDNS addon)
would also allow re-enabling `cluster.local` caching, which the Talos default
Corefile disables — that is why every internal lookup is a live query. One more
number for that work: **39% of everything CoreDNS forwards (1.48M of 3.79M) is
NXDOMAIN**, which is search-domain expansion leaving the cluster.

### 4. Un-mute `KubeCPUOvercommit` — belongs to the alerting work

It is routed to `null` on the reasoning that "cannot tolerate node failure" is
the intended steady state. **That was true when written** — it was firing at
8.399 against a 7.9 threshold.

It is no longer true. Requests are now **6.806 against 7.9**, and the alert has
stopped firing. That makes it an accurate early warning that N+1 has regressed —
the check most likely to rot as workloads are added.

This was deliberately left alone because the alerting config belongs to a
different work stream. The call to un-mute is theirs.

> One detail for whoever picks it up: the `10.4` figure in that mute's comment is
> `sum(kube_pod_container_resource_requests)`, which counts init containers
> separately. The alert uses the `namespace_cpu` recording rule, which was 8.399.

## Findings worth not rediscovering

**Addon settings leak into vclusters two ways.** Both cost a live incident on
2026-08-21 (nine Deployments frozen in `vcluster-media`):

1. An addon's values folder resolves by **chart name, not addon key**.
   `cert-manager-vcluster` has `chartName: cert-manager`, so it reads the *host's*
   `environments/production/addons/cert-manager/values.yaml`.
2. Several production-layer addons have **no `cluster_role` exclusion** —
   `kyverno` and `external-secrets` among them — so their ApplicationSets
   generate an Application for every production cluster, vclusters included.

Always render both bootstraps and diff which clusters each app targets. Do not
reason from the addon definition alone.

**vcluster's syncer does not propagate `priorityClassName`** to the host pod it
creates. Inside a vcluster that field satisfies admission but does not affect
placement.

**`:latest` is a live hazard here, not a style nit.** One rollout silently moved
`grafana-mcp` from 0.14.0 to 1.1.0 — a major version, three months of drift — and
the new build's `/healthz` rejected a stale token that the old one tolerated.
Separately, `platform-status-reconciler` ran a **2026-02-28** image for six
months because `:latest` means the manifest never changes, so ArgoCD has nothing
to sync. Both are now pinned; the reconciler deploys by bumping its
`main-<sha>` pin.

**Never point a *liveness* probe at an external dependency.** That is what turned
a Grafana credential problem into an endless pod restart. Readiness, yes;
liveness asks only whether the process is wedged.

## Working agreements that shaped all of this

From [CLAUDE.md](../CLAUDE.md), restated because they are easy to violate under
time pressure:

- **Git is the actuator.** Direct `kubectl` mutation is for orphans only, and you
  say so out loud when you do it. Two exceptions were taken this session and both
  are named above: the `kubectl rollout restart` that deployed the reconciler
  fix, and the annotation removal that is still pending.
- **Automation may restart and delete ephemeral objects. Anything that changes
  what *should* exist goes through a PR.** This is why the Kyverno cleanup
  controller is granted delete on Pods and Jobs only.
- **Never push to `main`.** Branch, PR, hand the merge over.
- **Verify by rendering.** Every addon change in this work was checked with
  `helm template` plus a `kubectl apply --dry-run=server`, and the sync policies
  by diffing the rendered ApplicationSets. That is what caught the
  16-of-48-apps-lost-selfHeal defect in the first place.
